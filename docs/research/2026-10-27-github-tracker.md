# GitHub Issues tracker: research (2026-10-27)

## Scope and recommendation

M11 spike for [plan open question 1](../plan.md#open-questions-for-v02), not a spec, decision record or M11 exit test. Inspected Stintwork checkout `8187208a10b622106b18000826835859350db921`, installed skills and upstream `mattpocock/skills` default branch `main` at `59db609eb1e18aaf59b63284d0e52255aff0c63c`. GitHub requests were read-only. No private repo or credential file was inspected.

**Recommendation:** Treat the parent issue body as the authoritative spec and GitHub issues as authoritative tickets; read them through `gh`. Store Stintwork-owned `workflow.yaml` and its gate records in a committed repo file keyed by the GitHub repository identity and parent issue number, read from the work item's worktree once it exists. Agents publish and edit issues using their configured skills; Stintwork never mirrors issue content back to GitHub. Approval must bind to the observed issue revision as well as the code commit, or a later remote edit could leave an apparently valid approval on a different spec.

This deliberately narrows ADR 0001's all-durable-state-in-repo rule: issue bodies and comments are durable remote state, unavailable in a clone or offline. M11 already calls for an ADR superseding [0005](../adr/0005-local-markdown-only-in-v1.md); a decision must also explicitly address the conflict with [0001](../adr/0001-repo-files-are-the-source-of-truth.md), rather than presenting the hybrid as compliant. It preserves 0005's no two-way synchronization and [0009](../adr/0009-work-item-files-come-from-its-worktree.md) for the files that remain local. Costs: remote read/refresh and access handling, a stable issue-to-worktree association, recording and rechecking remote revision evidence, and changes to the file-based index, brief and gates. Cross-system reads cannot be an atomic snapshot; failure or a changed revision must not silently approve stale content.

## What Stintwork reads today

`work-items.ts` indexes immediate `.scratch/<slug>/` directories. It keeps `spec.md` text intact, uses its first `# ` heading for the title, and reads one `issues/NN-<slug>.md` per ticket. The first plain or bold `Status:` and `Blocked by:` before the first `## ` section supply metadata; comments are blocks in the first `## Comments` section. A resolved/done/closed/complete/completed status satisfies a blocker; missing referenced tickets block and warn. The index orders dependencies before dependants, with numeric order as a tie-break and a warning/fallback for cycles. This is a line reader, not a full Markdown parser. See `packages/core/src/work-items.ts` and `work-items-to-tickets.test.ts`.

`detectSetup` reads `docs/agents/issue-tracker.md`, preferring its `# Issue tracker:` declaration, and recognizes GitHub or local Markdown by text patterns. Current Project setup proposes local Markdown; an existing non-local tracker is marked other-tracker and replacement is not selected by default (`setup.ts`, `setup-plan.ts`). Detection does not itself load GitHub issues. ADR 0006 puts state in the shared model, with views consuming it.

For a gate action, `packages/server/src/gates.ts` checks readiness, captures developer, time and current commit, updates stage/approval in `workflow.yaml`, and commits the workflow file through `workflow-writes.ts`; reopen is recorded too. ADR 0009 chooses the worktree copy when present. The gate tests exercise worktree isolation and the recorded commit. The current index and brief use local paths, so accepting a GitHub tracker requires more than a different setup label.

## The skills' GitHub layout

`to-spec` publishes the spec to the configured tracker, so under GitHub it is an issue body, with problem, solution, stories, decisions, testing and scope. `to-tickets` makes one issue per ticket; if the source was an existing issue it makes each a sub-issue and references the parent. It does not modify or close that parent. If there was no source issue, no parent is required: there is no guaranteed marker that identifies a parent or distinguishes a standalone issue from a work item. Acceptance criteria checkboxes in ticket bodies are not themselves ticket issues. Sources: pinned [to-spec](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/to-spec/SKILL.md), [to-tickets](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/to-tickets/SKILL.md), [tracker](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/setup-matt-pocock-skills/issue-tracker-github.md).

Tickets are published blockers first; native GitHub dependency edges are preferred, otherwise a `Blocked by` body section or `Blocked by: #n, #n` line names them. A closed blocker counts as satisfied in the GitHub tracker convention, including a closed-not-planned blocker; that differs from local tracking's resolved-only convention. There is no general explicit ticket-order field or guarantee that issue number encodes dependency order; derive a topological order and choose a documented tie-break. For Wayfinder specifically, the map is a `wayfinder:map` issue, children are sub-issues or a parent task list plus child `Part of #n`, and first in map order wins; this fallback should not be assumed for every `to-tickets` output. Native links, prose and task lists can conflict or be incomplete, so precedence is a spec question. [Tracker source](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/setup-matt-pocock-skills/issue-tracker-github.md).

Triage's configurable role labels mean: `needs-triage` needs maintainer evaluation; `needs-info` awaits reporter; `ready-for-agent` is specified for an unattended agent; `ready-for-human` needs human implementation; `wontfix` will not be actioned. Actual label names may differ according to `docs/agents/triage-labels.md`. Triage expects one state and one category (`bug` or `enhancement`), flags conflicting states, and closes `wontfix`; `to-tickets` normally applies `ready-for-agent`. These are triage roles, not a complete execution state machine. Wayfinder claims by assignment; no general in-progress label or universal rule that assignment means in progress is specified. Closed state and `stateReason` can distinguish completed from not planned, but do not assume every closed issue has a reliable reason or every `wontfix` is already closed. Sources: [labels](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/setup-matt-pocock-skills/triage-labels.md), [triage](https://github.com/mattpocock/skills/blob/59db609eb1e18aaf59b63284d0e52255aff0c63c/skills/engineering/triage/SKILL.md), [GitHub issue state](https://docs.github.com/en/rest/issues/issues#get-an-issue).

## Read-only access and observed results

With `gh` 2.94.0, authenticated on github.com, the following commands only read. Replace `OWNER/REPO` and `N` with the target. `--repo` prevents fork/upstream ambiguity; REST placeholders below are literal examples, not shell variables.

```sh
command -v gh
gh auth status --active --hostname github.com
gh repo view OWNER/REPO --json nameWithOwner,url,defaultBranchRef
gh issue list -R OWNER/REPO --state all --limit 100 --json number,title,body,state,stateReason,labels,assignees,parent,subIssues,blockedBy,updatedAt,url
gh issue view N -R OWNER/REPO --json number,title,body,state,stateReason,labels,assignees,comments,parent,subIssues,blockedBy,updatedAt,url
gh api 'repos/OWNER/REPO/issues/N' --jq '{number,id,node_id,state,state_reason,issue_dependencies_summary,sub_issues_summary,updated_at}'
gh api --paginate 'repos/OWNER/REPO/issues/N/sub_issues?per_page=100'
gh api 'repos/OWNER/REPO/issues/N/parent'
gh api --paginate 'repos/OWNER/REPO/issues/N/dependencies/blocked_by?per_page=100'
gh api --paginate 'repos/OWNER/REPO/issues/N/dependencies/blocking?per_page=100'
gh api --paginate 'repos/OWNER/REPO/issues/N/comments?per_page=100'
gh api rate_limit --jq '.resources | {core,graphql,search}'
```

`body` contains spec text, checkbox/task-list Markdown and text fallbacks; comments have their own bodies, authors, timestamps and IDs. REST issue `id` is a numeric database ID, `node_id` is GraphQL's opaque ID, and `number` is repo-scoped. REST dependency summary `blocked_by` counts open blockers, while `total_blocked_by` includes closed; list the edges for identity and state. `gh issue view --json blockedBy,subIssues` returned connections with `nodes` and `totalCount` in this version. Do not treat the count as a complete list, nor assume nested `gh` JSON connections or comments are unbounded: use paginated endpoints for completeness. REST issue-list endpoints may include PRs, identifiable by `pull_request`. Sources: [gh issue view](https://cli.github.com/manual/gh_issue_view), [REST sub-issues](https://docs.github.com/en/rest/issues/sub-issues), [dependencies](https://docs.github.com/en/rest/issues/issue-dependencies), [comments](https://docs.github.com/en/rest/issues/comments), [issues](https://docs.github.com/en/rest/issues/issues).

`gh issue list` defaults to open and 30 results; `--limit 100` is still a cap, not proof of completeness. REST `--paginate` follows pages; the endpoints above accept `per_page` up to 100, and output is one JSON array per page unless `--slurp` is used. GraphQL connections need independent cursor pagination and `pageInfo`; `gh api graphql --paginate` requires `$endCursor` and `pageInfo { hasNextPage endCursor }`. Large nested connections must be paginated independently. Sources: [gh issue list](https://cli.github.com/manual/gh_issue_list), [gh api](https://cli.github.com/manual/gh_api), [GitHub pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api).

`command -v gh` detects a missing executable; a non-JSON `gh auth status --active --hostname github.com` reports the active login and exits nonzero on auth problems. Its `--json` form normally exits zero even for auth problems, so inspect its data if used. Follow with a read of the explicit target repository/issues: login alone does not grant access. Distinguish a missing/inaccessible repo from offline, rate limits and server failure where possible; GitHub may return 404 for private resources without access, so 404 cannot prove absence. Do not use `--show-token` or read credentials. Sources: [gh auth status](https://cli.github.com/manual/gh_auth_status), [GitHub REST troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api).

Authenticated REST user requests normally have 5,000 core requests/hour; GraphQL normally has 5,000 points/hour, subject to GitHub's documented account/enterprise exceptions. Search is separately limited, and secondary limits can apply even before the primary limit. Respect `Retry-After`, rate-limit headers and reset time; avoid an unbounded per-issue request fan-out. The observed `gh api rate_limit` reported core 5,000, GraphQL 5,000 and search 30; remaining counts change. Source: [REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api).

Live read: [mattpocock/skills #1338](https://github.com/mattpocock/skills/issues/1338) returned `OPEN`, `needs-triage`, no assignees, comments, parent, sub-issues or blockers; REST summary reported zero and both paginated relation GETs returned `[]`. Parent GET returned 404 with “No parent issue found”: that response must not be generalized to no repository access. A read of 500 issues found no nonempty native parent/sub-issue/blocker connection. Thus actual nonempty relationship, pagination across multiple pages, private-repo access and end-to-end skills-created parent/ticket layout were **not verified**; their shapes above are documentation/skill-derived, not live proof.

## Open question 1: placement

| Option | Consequence against ADRs and M11 |
|---|---|
| Spec and workflow in branch files | Fits 0001 and 0009, review and offline use. A GitHub `to-spec` publishes an issue instead, so choosing a file as authority requires changing the skills/config or duplicating/syncing the spec, contrary to M11's proposed flow and 0005's rationale. |
| Spec and approvals in issue body | Native to `to-spec`; shared remotely. Breaks 0001 and bypasses 0009 for the spec; recording approvals by Stintwork would write GitHub and conflict with M11's read-only Stintwork boundary. Body edits also need a revision-sensitive approval. |
| Issue comments for approvals | Has authors and timestamps but is remote, can be edited/deleted, needs explicit commit and revision evidence, and requires Stintwork to write or depend on agents/humans doing so. Same 0001/0009 and read-only conflict. |
| Labels for approvals | Remote and requires writes; a label alone cannot record approver, time, code commit and spec revision, and can collide with triage labels. |
| Issue body for spec; `.stintwork/` workflow file keyed by repo and issue number | One authority per kind of data, no sync; gate records remain versioned and worktree-local under 0009. Remote spec violates 0001 and needs an explicit decision. A new path/key and mapping are Stintwork additions; issue transfer, renumbering and branch merge/conflict handling need design. |

A gate could store an issue `updatedAt` plus a content digest and issue identity alongside the code commit; the spec must define what is approved, include relevant comments if they form the spec, and re-fetch immediately before approval/use. `updatedAt` alone may change for unrelated events and is not a transaction or a content hash. If evidence cannot be refreshed, show unknown/stale and do not claim a current approval. Existing local gate records and checks still need their own commit semantics (`gates.ts`, ADR 0009).

## Mapping

| Stintwork term | GitHub representation | Gap |
|---|---|---|
| Work item | Parent issue whose body is the spec, or standalone issue | No universal parent/type marker; standalone and ticket can be ambiguous. |
| Ticket | Child issue / sub-issue; fallback `Part of #n` and possibly a parent task list | Source-less tickets need not have a parent; task list items need not be issues. |
| Spec | Parent issue `body` | No repo-file copy or immutable approval revision by default. |
| Ticket status | Issue `state`/`stateReason`, configured triage label, possibly assignee | No universal in-progress role; conflicting labels and not-planned closure need policy. |
| Dependency | Native `blocked_by` edges, fallback body references | Text syntax, cross-repo targets, inaccessible blockers and conflicting representations need policy. |
| Gate | Stintwork workflow file and recorded approval, checks or merge | No corresponding skill-defined GitHub gate; approval must bind remote evidence. |
| Comment | Issue comment records | Separate remote records, editable/deletable; local parser expects a `## Comments` section. |

Mapping sources: glossary and code above; pinned tracker, to-tickets and triage sources; GitHub REST documentation linked in the access section.

## Questions for the spec

- How are work items discovered, including standalone issues, orphan tickets, nested or cross-repo sub-issues, PRs sharing the issue number space, and user-defined labels? How are issue identity, transfers, deleted issues and repo renames handled?
- Define native vs text/task-list precedence, order, cycles, missing or inaccessible blockers, closed-not-planned blockers, multiple/conflicting triage labels and assignment semantics. Never show unknown dependencies as unblocked.
- Define refresh on opening, after stints and before gate actions; show last successful fetch, partial pages and stale data. A cached snapshot is not authority; choose whether offline use exposes a clearly stale read-only view or no remote data. Handle remote edits while a worktree is active and simultaneous local changes.
- Define private-repo authorization, host/remote selection, revoked or expired login, 404 ambiguity, rate limits, enterprise feature availability and recovery without storing tokens. Do not leak cached private issue content across projects or users.
- For thousands of issues, bound initial discovery and concurrent requests, paginate every required connection, load bodies/comments/edges on demand, and measure latency and rate use. Specify filtering and a way to know results are incomplete; do not silently cap at 30 or 100.
- Define approval evidence and invalidation for remote body/comments versus code commits, including reopening and stale review/checks, plus branch creation, merges and conflicts for the issue-keyed workflow file. No atomic transaction spans GitHub and git.
