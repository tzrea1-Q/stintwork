# Stintwork v0.1.0

Unreleased. The npm package is prepared but not yet published.
Publishing to npm and making the GitHub repository public are separate steps. Each needs the maintainer's explicit confirmation.

## What v0.1 does

Stintwork is a local workbench for one developer and their own coding agents. It takes a work item through stages, from an idea to a merged change.

A stint is one agent's turn on a stage, optionally on a ticket. It starts with a brief and ends with a handoff. A gate must pass before a stage advances. **Shipped means merged**, not just a finished stint or an approved gate.

### Board and workflows

The Pipeline view shows work items by stage, with milestone filters and a drawer for specs, tickets and stint history. File edits update the board without a reload. Existing work items can have their stage inferred from their files.

Create a work item from the board with a title, intent, workflow and optional milestone. Its folder is previewed before confirmation. Creation makes one commit.

The built-in workflows are:

- Feature: Clarify → Spec → Tickets → Implement → Review → Ship.
- Bug: Diagnose → Fix → Review → Ship.
- Quick: Do → Review → Ship.

Use **Customise** to preview and copy a built-in workflow into `.stintwork/workflows/`. Edit its YAML to change skills, agents or ordered stages. Project workflows can override built-ins or add new choices. Invalid files produce warnings and fall back rather than hiding work items.

### Stints, Needs you and gates

Preview the brief before starting. It names the stage skill and project files, includes your intent and the last handoff, and lists changes since that handoff. Each work item has its own worktree. Once it exists, edit the spec and tickets there; the drawer shows the path.

Watch messages, tool calls, plans and file edits in the stint stream. Stop a stint when needed. Stintwork records its checkpoint and requests a handoff. The next stint can use another agent without transferring the conversation. History can be replayed after a restart.

**Needs you** collects questions, permission requests, login requirements, gate approvals and memory proposals. Answer unresolved handoff items with a developer note for the next brief. Changes to the glossary, decision records and `AGENTS.md` become memory proposals for you to accept or reject.

Clarify ends with your judgement. Spec needs a parsing `spec.md` in the work item's folder. Tickets needs at least one valid ticket and valid dependency order. The gate view names missing output. Approvals are committed in `workflow.yaml` with who approved, when and at which commit.

### Review and shipping

Review stints check Standards and Spec without implementing fixes. Inspect the diff and findings. Resolve each finding, accept it with a reason or send it back for implementation.

Local checks run in the worktree. Defaults use existing `test`, `lint`, `typecheck`, `build` and `format:check` scripts. An explicit `checks` list in `.stintwork/config` replaces those defaults. Findings and check results are tied to a commit. Code changes make old evidence stale. Review cannot advance until evidence is current, findings are decided, checks pass and no memory proposals remain open.

Ship by merging locally, or by opening a pull request through `gh`. The pull request path requires confirmation before any push. Merge requires passing pull request CI and current approved Review evidence. The confirmation shows the merge method. After a successful merge, Stintwork records it, removes the worktree and branch, and shows Shipped with history intact.

### Setup, roadmap and package

Guided setup previews missing tracker conventions, agent instruction pointers, a local-log ignore entry and a starter roadmap. You select the changes and confirm one commit. Existing instruction content is preserved. Uncommitted target files are refused.

Setup also reports stage skills as found, missing or can't tell. It never installs skills or changes agent configuration. **Edit roadmap** adds, renames and reorders milestones, changes their status or target date, and moves work items. Each edit is one commit and keeps hand-written text.

The prepared package includes the CLI, server, web app and workflow YAML. It includes the Claude Code and Codex ACP adapter dependencies and has no native dependencies. Stintwork is licensed under Apache-2.0.

## How to start

You need Node.js 22.12 or newer, Git and at least one installed Claude Code or Codex CLI on PATH. Use your own signed-in agent. One agent is enough.

Sign in to the one you choose:

```bash
claude auth login
```

Or:

```bash
codex login
```

Until npm publication, build a local Stintwork checkout with pnpm, then start it from your project's main checkout and main branch:

```bash
cd /path/to/stintwork
pnpm install
pnpm build
cd /path/to/your/project
node /path/to/stintwork/dist/bin.js
```

Replace the example paths with absolute paths. Commit the project files you want the agent to see before its first stint.

After publication, the intended entry point inside your project's git repository is:

```bash
npx stintwork
```

The CLI prints a local address and opens the browser. Keep the terminal open. Use `--no-open` to open the printed address yourself, `--help` for options and `--version` for the package version. Ctrl+C stops the server.

For a first work item:

1. Open **Setup**, inspect the proposed files and apply only the changes you want. Check the stage skills and follow the installation hints yourself if needed.
2. Press `c`, or use **Create work item** in the command palette (Command+K or Ctrl+K). Choose Feature and describe a small change.
3. Preview and start each stage's stint. Answer Needs you items and approve Clarify, then read and approve the spec and tickets.
4. Implement ready tickets in dependency order. If you stop a stint, inspect its checkpoint and handoff before resuming.
5. Run Review and local checks. Decide findings and memory proposals. Obtain fresh evidence after any code changes, then approve Review.
6. Choose **Merge locally** in Ship. It needs no remote or `gh`. Inspect any conflict or dirty-file refusal before retrying. Confirm the board shows Shipped.

The [getting-started guide](../getting-started.md) explains every stage, the expected files and check configuration.

## Verified agents and evidence

- **Claude Code:** adapter 0.88.0 passed basic, commands, permission and resume. The cancel probe did not exercise cancellation: Claude backgrounded `sleep` and ended its turn before cancellation. Stopping real Claude stints works.
- **Codex:** adapter 2.1.1 passed basic, commands, cancel and resume. Its permission scenario did not trigger because Codex runs commands without asking by default. This is the known behaviour described by the permission-level warnings.
- **Grok Build:** experimental and not verified end to end. Rate limits prevented the milestone verification. Its ask-mode permissions remain untested.

The coordinator recorded these release results on 2026-10-11:

- The packed-tarball smoke test passed locally and in CI on `ubuntu-latest` and `macos-latest`. Installation used 128 packages with no native modules.
- The full run used the installed tarball on a fresh tiny greet CLI project without mattpocock's layout. Guided setup from the Setup chip made one commit and found skills for Claude Code and Codex. A Feature work item was created with `c`.
- Real Codex stints covered Clarify, Spec, Tickets, Implement and Review. Clarify questions were answered with a developer note. Implement passed 5 tests. Review reported no findings. The test check passed on the head commit, then the Review gate was approved and Merge locally succeeded. The work item shows Shipped with its 5 stints and the check.
- Earlier M5 checks on a second project used Claude for Clarify and Spec and Codex for Tickets. A real pull request was opened and closed on a private GitHub repository.

These checks do not cover the separate M5 exit test with 3–5 developers outside the project.

## Known limitations

- Grok Build is experimental and not verified end to end. Use Claude Code or Codex for a first work item.
- There is no terminal fallback for agents without ACP. It is deferred to Later.
- The tracker is local Markdown only. Stintwork does not read or sync GitHub Issues. GitHub pull requests and CI use `gh` separately.
- Only one stint can be active per work item. Different work items can have active stints at the same time.
- Ask, Edit freely and Autonomous depend on each agent's own capabilities. They are not an independent security boundary. Codex can run commands without asking. Stintwork can only decide permission requests the agent sends.
- The `gh` pull request flow was tested against real GitHub for open/close and merge-method selection. The actual `gh pr merge` path and post-merge cleanup are covered by tests with a fake `gh`, not a completed real GitHub merge.
- Skill detection is best-effort. Found means a file exists in a supported location, not that its skill was tested. Stintwork does not install agent CLIs or skills, or handle credentials.
- Server restarts interrupt active stints; they do not reattach to agent processes. Continue through a new stint from the recorded state.
- Rejecting a memory proposal restores the whole file to that stint's starting version, including later committed changes. Inspect the diff and warning first.
- Workflows are ordered stage lists, not branching workflows. Every workflow must end with a merge gate in the Ship column.
